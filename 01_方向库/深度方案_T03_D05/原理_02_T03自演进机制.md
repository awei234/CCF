# 原理 02：T03 Agent 自演进机制（Auto Harness 深度解析）

> 目标：把「自演进」从概念讲成**机制**——Auto Harness 是什么、分几层、每条 pipeline 每阶段干什么、关键机制怎么工作、配置在哪、怎么触发、以及它如何与 SAR 评分咬合成"进化压力测试"。
> 本文件基于对 `auto_harness/service.py`（3016 行）、scheduler、task_store、openjiuwen 侧 orchestrator/pipelines/stages/prompts/skills/resources 的逐层源码探索。
> 更新日期：2026-08-11

## 1. 本质：Harness 层"后训练"

**一句话**：LLM 的"预训练"= 出厂教育（改模型权重）；Auto Harness 的"后训练"= 在岗位上继续学习（**改的是 Harness：prompt / tool / rail / skill，不改模型权重**）。

| 概念 | 传统 LLM | Auto Harness |
|---|---|---|
| 预训练 | 数据中心学知识 | Harness 出厂配置 |
| 后训练 | SFT / RLHF / RLVR（改权重）| **改 prompt/tool/rail/skill**（改"身体"）|
| RLHF | 人类反馈驱动的对齐 | **评测驱动闭环**（评估 → 差距 → 修改 → 再评估）|

**为什么"后训练"这个词贴切**：Agent 的智能 = Model（大脑）× Harness（身体）。想提升 Agent 表现，除了换更强的模型，更便宜高效的路是**改进 Harness**——而 Auto Harness 把"改进 Harness"这件事本身自动化了。

**对论文的意义**：这本身就是 T03 的方法论核心——"我们提出用 Auto Harness 对科研 Agent 做 Harness 层后训练"。对照 FARS（无自演进），这是创新点。

## 2. 两层架构（改哪一层，决定产出什么）

```
┌─ Meta Harness（通用底座层）──────────────────────────────────┐
│ 所有 Agent 共享：prompts / tools / rails / skills 基础组件     │
│ 优化方式：修改源码 → CI 验证 → 提 PR → 人工审查 → 合入主干     │
│ 安全边界：每次改动需 PR 审查（不可热加载）                     │
│ ★ 我们的用法：让系统改进底座并提 PR = 合规交付物 + 论文叙事    │
└──────────────────────────────────────────────────────────────┘

┌─ Expert Harness（领域扩展层）────────────────────────────────┐
│ 领域能力：办公 / 合规 / 内容生产等"专家能力包"                 │
│ 优化方式：生成 Harness Package → 热加载 → 即插即用（无需重启）│
│ ★ 我们的用法：让系统改进"科研严谨性扩展包" = 自演进实验主力    │
└──────────────────────────────────────────────────────────────┘
```

**两条层的产出物对比（关键决策依据）**：

| | Meta（改底座） | Expert（扩展包） |
|---|---|---|
| 产出 | git commit + **PR** | **Harness Package**（可热加载）|
| 生效方式 | 合入主干后 | 运行时注入，**无需重启** |
| 触发 pipeline | `optimize_meta_harness` | `optimize_expert_harness` |
| 对比赛的意义 | 框架贡献交付物（PR 链接）| 自演进实验（E2）数据源 |

> 详见 深度方案 README §3.1 的决策记录：**Expert 做实验，Meta 做交付**。

## 3. 两条 Pipeline 全阶段解析

### 3.1 概览对比

| | Meta Evolve Pipeline | Extended Evolve Pipeline |
|---|---|---|
| 阶段流 | assess → plan → implement → verify → commit → publish_pr → learnings | assess(gap) → select_pipeline → design_ext → implement_ext → verify_ext → build_verify → merge → activate |
| 终止条件 | 创建 GitCode PR | Package 热加载激活 |
| 单任务规模 | ≤3 源文件，限 `openjiuwen/harness/**`、`openjiuwen/core/**` | 生成 `openjiuwen/extensions/harness/<name>/` 扩展 |
| 隔离 | 独立 git worktree（assess 用只读快照）| worktree + 合并器 |
| 触发 | `/auto-harness run --pipeline optimize_meta_harness` | `/auto-harness run --pipeline optimize_expert_harness`（**service 默认**）|

### 3.2 Meta Evolve Pipeline（逐阶段）

| 阶段 | 由谁驱动 | 输入 | 做什么 | 输出 |
|---|---|---|---|---|
| **assess** | assess skill（`repository_health_assessment` 模式）| query + repo 只读快照 | ①读源码结构 ②`git log` 近 15 条 ③读经验库 ④Python 健康检查 ⑤`gh` 调研竞品做能力差距分析 ⑥查失败经验 ⑦输出结构化报告 | 评估报告（竞品对比表：竞品/功能/当前状态/差距/影响/可行性/建议方案/目标文件）|
| **plan** | plan skill | 评估报告 + 经验库 | 制定**单个最高优先级任务**（优先级：CI 修复 > 能力差距 > Bug > UX > 自驱动 > 竞品追赶）| 1 个 OptimizationTask（≤3 源文件、20 分钟内可完成）|
| **implement** | implement skill | task | 在 worktree 做最小代码改动，**停在未提交状态** | 变更 diff + commit facts |
| **verify** | verify skill（L1–L4 分级）+ CI gate | diff | lint / type-check / 分级验证；失败进 **fix_loop 自动修复**（phase1 最多 10 次、phase2 最多 9 次，超限 revert）| 验证通过 |
| **commit** | commit + communicate skill | commit facts | 本地 git commit（conventional commits）| commit |
| **publish_pr** | publish_pr + pr_draft prompt | 已提交 worktree | fork push → 按 GitCode PR 模板创建 PR（`/kind bug|task|feature|refactor|clean_code`）| **PR 链接** |
| **learnings** | learnings prompt | 本次经验 | 反思沉淀（novelty + 改变未来行为双门过滤）| 经验库条目（type: optimization/failure/insight）|

### 3.3 Extended Evolve Pipeline（逐阶段）

| 阶段 | 由谁驱动 | 输入 | 做什么 | 输出 |
|---|---|---|---|---|
| **assess** | assess skill（`runtime_extension_gap_assessment` 模式）| query | ①理解目标 ②识别目标产物 ③梳理输入输出 ④映射组件（Tool 执行动作 / Skill 承载知识 / Rail 介入生命周期，选最轻组合）⑤分析能力缺口 ⑥输出差距表 | GapAnalysisArtifact（差距表，固定列：竞品/功能/当前状态/差距/影响/可行性/建议方案/目标文件）|
| **select_pipeline** | select_pipeline skill | assessment | **固定选 extended**（prompt 强制 `pipeline_name=extended_evolve_pipeline`，fallback 也同值）| PipelineSelection JSON |
| **design_ext** | design_ext skill | GapAnalysisArtifact | 研究扩展框架 → 选组件类型 → 设计自包含扩展（file_plan + harness_config.yaml + 产物契约）→ **硬约束独立建模为 `kind="constraint"` 的 rail** | list[ExtensionDesign]（persist 到 `extension_design_*.json`）|
| **implement_ext** | implement_ext skill | ExtensionDesign | 在 worktree 生成 `openjiuwen/extensions/harness/<name>/`（tools/rails/skills/requirements.txt/harness_config.yaml，schema_version: harness_config.v0.1），**停在未提交状态** | 扩展代码 |
| **verify_ext** | verify_ext skill | 生成的扩展 | L1 结构校验 / L2 临时 DeepAgent 热加载 / L3 行为验证；失败归因码：`manifest_invalid / entry_point_not_allowed / module_import_failed / class_init_failed / skill_manifest_invalid` | 验证通过 |
| **build_verify** | CI gate / runtime_extension_merger | 多个扩展 | 合并多扩展、静态检查 | 合并产物 |
| **merge** | merge stage | 合并产物 | promote 到 `runtime_extensions/<hash>/` | 运行时扩展 |
| **activate** | ExtendActivateStage + activate_guide prompt | RuntimeExtensionArtifact | **用户确认 → 热加载激活**（`__interaction__`；auto_accept 时自动激活）→ 生成 **Harness Package** | 激活的 Package（可 import/export）|

### 3.4 阶段终止判定（怎么算"成功"）

- extended：`build_verify` 出现过 **且** `activate` 为 success/skipped → 成功
- meta：所有 slot 为 success/skipped → 成功
- 终结事件：`harness.session_finished` + `is_terminal: True`

> 探索来源：`run_log_status.py` 的 `META_EVOLVE_STAGE_ORDER` / `determine_pipeline_status_from_log`。

## 4. 关键机制（为什么它靠得住）

| 机制 | 作用 | 实现 |
|---|---|---|
| **Worktree 隔离** | 改进任务不污染主工作区；assess 用只读快照 | `infra/worktree_manager.py` |
| **CI 门控** | 质量红线：`make check` / `make type-check`（required）；immutable_files 不可改（identity.md/ci_gate.yaml 等）；high_impact 目录（core/**）改动需人批 | `resources/ci_gate.yaml` |
| **fix_loop 自动修复** | verify 失败自动重试修复，phase1 10 次 / phase2 9 次，超限 revert | `infra/fix_loop.py` |
| **预算控制** | session 总预算（session_secs 默认 900000s）、成本上限（cost_limit_usd 默认 $10）、单任务超时、每 session ≤5 任务 | config `budget:` 段 |
| **经验库** | 每次 learnings 沉淀经验，后续 plan/assess 参考历史（type=optimization/failure/insight）| `experience/experience_store.py` + synthesizer |
| **运行时扩展加载** | Package 热加载真实机制：`runtime_extension_loader` 动态注入 + `agent.load_harness_config(config_path)` 生效，无需重启 | `infra/runtime_extension_loader.py`、`openjiuwen/harness/deep_agent.py` |

**对我们的直接意义**：这些机制意味着 Auto Harness 改 rail 是**安全、隔离、可回滚、有预算红线**的——我们可以放心让它"进化我们的 rail"，不会把系统改坏。

## 5. 配置结构（在哪配、配什么）

### 5.1 配置位置

- **不在** jiuwenswarm 的 `resources/config.yaml`（无 auto_harness 段）
- **在** openjiuwen 侧：`~/.openjiuwen/auto_harness/config.yaml`（由 `load_auto_harness_config` 引导创建）
  > 🔧 **2026-08-12 源码核查修正**：本工作区 jiuwenswarm 0.2.4b4 实测配置路径为 **`~/.jiuwenswarm/auto-harness/config.yaml`**（`service.py:72,239`），openjiuwen 文档假设 `~/.openjiuwen/auto_harness` 不适用——见 `细化_04` §修正记录。
- TUI 编辑：`/config edit` 或 `/status config`（`/config edit` 项：`auto_harness_git_user_name / auto_harness_git_user_email / auto_harness_gitcode_access_token`）

### 5.2 完整字段（openjiuwen `resources/config.yaml`，72 行）

```yaml
# 顶层可选：local_repo / repo_url / pipeline(auto|meta|extended) / language(cn|en) / skills_dirs / immutable_files / experience_dir
git:
  remote: ""                          # fork remote 名（如 autoharness）
  base_branch: "develop"              # PR 目标分支（模板默认 develop-auto-harness，build 时覆盖为 develop）
  user_name: ""                       # ★必填 git commit 用户名
  user_email: ""                      # ★必填 git commit 邮箱
  fork_owner: ""                      # fork 所有者（缺省时写 user_name）
  upstream_owner: "openJiuwen"        # 上游所有者
  upstream_repo: "agent-core"         # 上游仓库
gitcode:
  username: ""                        # GitCode 登录名
  access_token_env: "GITCODE_ACCESS_TOKEN"   # token 从环境变量读
budget:
  session_secs: 900000                # 会话总预算（秒）
  cost_limit_usd: 10.0                # 单会话成本上限（美元）
  task_timeout_secs: 300000           # 单任务超时
  model_timeout_secs: 300000          # 单次 LLM 请求超时
  max_tasks_per_session: 5
ci_gate:
  config_path: ""                     # ci_gate.yaml 路径
  python_executable: ""
  install_command: ""                 # 例: uv sync --active --group dev --extra cli
fix_loop:
  phase1_max_retries: 10
  phase2_max_retries: 9
agent:
  implement: 60                       # assess/plan/implement: 60
  # select_pipeline/eval/pr_draft/learnings: 20（各阶段 max_iterations）
extensions:                            # ★源码贡献机会（见 §7）
  stage_registrars: []                # module:callable, (StageRegistry)->None
  pipeline_registrars: []             # module:callable, (PipelineRegistry, StageRegistry)->None
```

### 5.3 必填项（ConfigValidator 校验）

- `git.user_name`（必填，写入时联动写 `git.fork_owner` + `gitcode.username`）
- `git.user_email`（必填）
- `gitcode.access_token`（可选，环境变量 `GITCODE_ACCESS_TOKEN` 可替代）

### 5.4 模型来源

- service/scheduler 的模型从 jiuwenswarm `config.yaml` 的 `models.defaults` / `react` 段继承（即我们配的 DeepSeek）。

## 6. 触发方式与"进化压力测试"

### 6.1 触发命令（TUI `/auto-harness`）

```bash
# 一次性任务（核心用法）
/auto-harness run [--pipeline optimize_meta_harness|optimize_expert_harness] <query>

# 定时任务（让系统持续进化）
/auto-harness schedule start --interval 24 <query>   # 每小时可选 1/2/4/8/12/24

# GitCode issue 驱动（让系统修别人的 issue → 提 PR）
/auto-harness issue scan / issue fix <numbers>
```

### 6.2 自演进闭环 × SAR 评分（论文 E2 的核心咬合）

```
科研流水线产出论文 ──→ SAR 打分（6 维 + 修改建议）
        ▲                                │
        │ 改进后的 rail/skill            ▼
        │                   /auto-harness run --pipeline optimize_expert_harness \
        │                   "分析最近 3 篇论文的 SAR 反馈，评估科研严谨性扩展包的缺口，
        │                    设计并实现改进（rail/tool），热加载生效"
        └──────── 验证效果 ←────────── 重新生成论文 → 对比 SAR
```

**要点**：
- SAR 每一轮反馈（6 维分数 + 修改建议）= 自演进闭环的**进化压力测试**（fitness function）
- Expert pipeline 的 assess（gap 评估）天然适配"读 SAR 反馈 → 找缺口"
- design_ext 的产物契约（rail 组件建模、硬约束独立为 constraint rail）= 正好产出我们要的 rail
- 一次进化 = 一次 E2 实验数据（前后 SAR + rail 差异）

### 6.3 scheduler 说明

- 定时任务默认走 `META_EVOLVE_PIPELINE`；无交互通道 → `auto_accept=True`（自动确认所有 interaction）
- 日志落盘：`~/.jiuwenswarm/auto-harness/runs/{task_id}/{execution_id}/log.json`（JSON Lines）
- 状态机：pending → running → success|failed|cancelled；启动时 reconcile 陈旧状态

## 7. 源码贡献机会（向 openJiuwen 提 PR 的抓手）

探索发现 Auto Harness 配置中有扩展注册点：

```yaml
extensions:
  stage_registrars: []    # module:callable → 注册自定义 Stage
  pipeline_registrars: [] # module:callable → 注册自定义 Pipeline
```

**可做的贡献方向（竞赛"框架贡献" + PR 链接）**：
1. 新增一个**科研场景专用 Stage**（如 `paper_consistency_check`），注册进 extended pipeline
2. 新增一个 **verify_ext 的验证器**（科研产物校验：PDF 头/JSON schema/数字勾稽）

> 这些都是"框架级"贡献：别人也能用，评审认可度高；同时全部服务于我们自己的系统。

## 8. 风险与可控性（结合我们的时间预算）

| 风险 | 现实 | 缓解 |
|---|---|---|
| 环境门槛 | Meta pipeline 需 GitCode 认证 + worktree + CI | 阶段 0 就配好 git/gitcode；先用 Expert 层（不碰 CI/PR）|
| 稳定性 | 多步 agent 交互可能中途失败 | fix_loop 自动修复兜底；scheduler 日志可查 |
| 成本 | 一次 run = assess+design+implement+verify，Token 不小 | `budget.cost_limit_usd` 设 $10 红线；先用小 query 试跑 |
| 时间 | 59 天，演进闭环是增量 | **先做确定性的 F02/03/04（T04 兜底），阶段 5 再赌演进（T03 升格）** |

> 核心策略回顾：F02/F03/F04 是 T03 和 T04 的公共地基，先做不亏；阶段 5 演进实验成了 → T03 主叙事；不成 → T04 主叙事，自演进写 Future Work。
