# F06 资源预算与日志 Rail（交付物保障）

> 分组：F 功能模块 ｜ 实现成本 低 ｜ 影响维度：资源报告交付物 + 成本控制
> 状态：阶段 2 同步开发 ｜ 更新日期：2026-08-11

---

## 1. 模块定义

一套资源管理机制：① 在 plan 阶段做 **Token/时长预算估算**（FARS 附录 B 的预算公式）；② 全程记录 **Token 消耗/运行时长/算力日志**（比赛硬性交付物"资源报告"的数据来源）。

**一句话**：比赛要求交资源报告，从第一天起就记录，别到最后补。

## 2. 为什么重要

- 提交物③资源报告：Token 消耗、运行时长、算力日志（可追溯）——**硬性要求**
- FARS 局限 1"算力利用率低"（1.14 亿 Token/篇）是我们的成本对标点：$10 量级 vs $1,040
- 预算估算强制 agent 想清楚再动手，顺带提升计划质量

## 3. 功能规格

### 3.1 预算估算（plan 阶段）
- 按 FARS 附录 B 公式：阶段 Token 估算 = 输入/输出 × 阶段轮数 × 迭代系数
- plan.json 增加 `budget` 字段（F02 联动校验）

### 3.2 日志记录（全程）
| 记录项 | 来源 | 落点 |
|---|---|---|
| Token 消耗（in/out）| 每次模型调用 | 07_记录/资源日志.md（或结构化 csv）|
| 运行时长 | 阶段起止 | 同上 |
| 算力日志 | 机器资源 | 同上 |
| 成本 | Token × 单价 | 同上（单篇汇总）|

### 3.3 成本红线
- 单篇论文目标：**$10 量级**（DeepSeek 下远低于 FARS 的 $1,040）
- rail 可设熔断：某阶段超预算时提示精简/暂停

## 4. 实现要点

- 优先做**日志工具**（不依赖 rail 机制）：`tools/resource_logger.py`，在每个阶段入口/出口打点
- rail 版本可选：`code/rails/budget_rail.py`（before_tool_call 检查预算余量）
- 与 JiuwenSwarm 观测能力结合：`agents/harness/agent_observability.py`（OTEL）可复用
