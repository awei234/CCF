# 各阶段详细执行手册（阶段 1–8）

> 本手册是「从零开始行动路线.md」的深化版：每个阶段回答三个问题——**具体怎么做（操作步骤）/ 为什么这么做（原理）/ 有什么意义（对评分、论文、合规的价值）**。
> 阅读顺序：先看每个阶段的「目标」和「类比」，再细看步骤。
> 关联：`01_方向库/深度方案_T03_D05/`（技术原理）、`00_比赛总览/评分体系拆解.md`（评分机制）。
> 更新日期：2026-08-14（阶段化批）

---

## 总览图

```
阶段1 最小闭环  阶段2 三个rail   阶段3 A/B+E1   阶段4 写作质量   阶段5 自演进+PR   阶段6-8 交付

```

**贯穿原则**：先确定后不确定——F02/F03/F04（T04 兜底）永远先做，Auto Harness（T03 升格）是增量赌注，任何时候都不影响主路径。

## 阶段 1：最小闭环

### 目标
- 产出第一篇可提交的论文 PDF
- 拿到 SAR 基线分（6 维），存入 `05_评测与迭代/基线分.md`

### 类比
先别想造火箭，先让"能写论文的机器"跑起来——哪怕质量一般。第一篇论文是"样机"，不是"成品"。

### 具体怎么做
1. **建 skill 骨架**：`03_技术实现/custom_skills/research-pipeline/`
   ```
   research-pipeline/
   ├── SKILL.md        # frontmatter(name/description/trigger/allowed_tools/tags) + 流程总览
   ├── prompts/
   │   ├── ideation.md     # 选题拆解（Schulman 选题法 + novelty 三步验证）
   │   ├── planning.md     # 方法设计（plan.json 结构）
   │   ├── experiment.md   # 实验执行（workspace 规范）
   │   └── writing.md      # 论文撰写（ICLR 模板、数字一致）
   └── references/         # 渐进式披露的深度资料
   ```
2. **把 FARS 附录 B 的 prompt 改写成中文 skill 内容**（素材在 `02_情报库/FARS标杆分析/fars_paper_text.txt`）——别人实验验证过的操作手册，直接改编
3. **配置 skill 的 allowed_tools**：写文件、读文件、bash、搜索/网络
4. **触发**：在 CLI 里让 agent 按 skill 跑完整流程，产出 `paper.tex`
5. **LaTeX 编译 PDF**：`pdflatex paper.tex`（服务器装 texlive 或本地编译）
6. **提交 SAR**：上传 PDF 到 https://paperreview.ai → 记录 6 维分 + 修改建议

### 为什么这么做
- **基线分 = 后续所有实验的"对照组"**。没有它，你永远无法证明 rail 有没有用、改了有没有变好——A/B 实验必须有 0 号样本
- **先走最简单路径**（skill 是官方"基本思路"），把"触发→生成→编译→评测"全链路暴露一遍。链路问题（skill 触发失败、LaTeX 报错、评测流程）现在暴露比阶段 5 暴露好一百倍
- **FARS 附录 B 是免费手册**：Cornell 用 117 篇论文实测验证过的 prompt，抄框架不丢人，省掉大量试错

### 意义
- 建立「生成 → 评测 → 迭代」闭环的第一个循环，后面每轮都在这个循环上转
- 拿到自己的分数起点（E3 基线对照里"我们"的锚点）
- 暴露环境缺口（比如缺 texlive），提前补

### 验收
- [ ] skill 可被 agent 触发并完整走完四阶段
- [ ] paper.tex 编译出 PDF
- [ ] SAR 6 维分记录在案

## 阶段 2：主线开发：三个 rail

### 目标
- F02（实验规划）/ F03（结果一致）/ F04（引用核验）实现、单测通过、挂载生效
- 论文 v2（带 rail）提交 SAR，第二轮正式提交

### 类比
阶段 1 的机器会写论文了，但会瞎编。本阶段给机器装**质检员**：不合格的产品根本过不去。

### 具体怎么做
1. **精读 3 个参考 rail**（`原理_03` §8）：tool_restriction（拦截协议）、project_memory（注入协议）、plan_approval（状态机）
2. **定义产物协议**（这是三个 rail 的地基，先在 `custom_rails/` 里定 schema）：
   - `plan.json`：experiments[]（baselines≥2、ablation 前置、seeds≥3、budget、datasets 独立声明）+ reproducibility
   - `results.json`：每实验一个，含 metrics 数据
   - `workspace/`：plan.json → experiments/*/results.json → paper/paper.tex
3. **F02 实验规划 Rail**（priority 50）：
   - 钩子 `before_tool_call`：拦截 plan.json 写入 → 校验 schema → 不达标 `_skip_tool` + tool_msg 打回（附问题清单）
   - 钩子 `after_tool_call`：标记 `_plan_valid` 供 F03 勾稽
4. **F03 结果一致性 Rail**（priority 45）：
   - 钩子 `after_model_call`：提取论文数字 → 与 results.json 匹配（精确/推导）→ 未验证清单注入系统提示让模型下一轮修正
   - 与 F02 联动：plan 声明的实验必须都有 results.json
5. **F04 引用核验 Rail**（priority 40）：
   - 工具 `tools/citation_checker.py`：arXiv API + Semantic Scholar API 双通道
   - rail 触发核验 → 假引用/未核验引用列入修正清单（容错：网络失败不误杀）
6. **单测**：构造 `AgentCallbackContext` 直接调钩子（参照 test_code_task_planning_rail），每个 rail 4 个用例
7. **开发期热加载挂载**：rail 放 `extensions/<name>/rail.py` → `hot_reload_rail` 生效（不重启服务）
8. **生成论文 v2** → SAR → 对比基线分
9. **第二轮提交**：zip 打包（`06_提交物/提交物清单.md`）

### 为什么这么做
- **FARS 实测三大失败模式是全场通病**：捏造结果最高 77%、实验支撑不足 49.6%、计划执行不匹配 23.9%。用机制（rail）强制解决 = 差异化，绝大多数队伍只堆 prompt
- **Rail 是官方"进阶思路"**（"修改 JiuwenSwarm 源码，通过 rail 拓展 harness 能力"）= 同时满足比赛"必须改源码"硬性要求
- **实验严谨性维度 15% 权重 + 决赛复现审核生命线**：论文数字与 results.json 一致，复现审核就不会翻车

### 意义
- 技术核心，论文 **Method 章节**的素材（rail 架构、钩子设计）
- 合规（改源码的证明）+ 评分（实验维度）+ 安全垫（决赛复现）三重价值
- 三个 rail 是 T03/T04 两条主线的公共地基，**永远不白做**

### 验收
- [ ] 三个 rail 单测通过（合法/非法场景）
- [ ] rail 在流水线真实拦截过一次不合格操作
- [ ] 论文 v2 提交 + 记录分数

## 阶段 3：A/B 迭代 + E1 实验

### 目标
- 建立 SAR 反馈闭环（修改→提交→对比）
- E1 实验数据：有 rail vs 无 rail 对比（论文"实验严谨性"章节核心证据）

### 类比
质检员装好了，本阶段**证明它值钱**——用实验数据说话。

### 具体怎么做
1. **建提交记录模板**：`05_评测与迭代/提交记录.md`（版本/改动点/SAR 六维/建议/下一轮假设）
2. **每 2 天一轮 A/B**：
   - 读 SAR 6 维 + 修改建议 → 定 1 个修改假设（如"实验维度低 → 加 baseline"）
   - 改 rail/prompt → 重新生成论文 → 提交 → 记录
   - 对比上一轮，验证假设
3. **E1 实验**（核心）：
   - 对照组：skill 无 rail，5 篇
   - 实验组：skill + F02/03/04，5 篇
   - **控制变量**：同模型（deepseek-v4-flash）、同主题池、同 seed 策略——唯一变量是 rail
   - 测 4 指标：捏造率（未验证数字/总数字）、支撑率（plan 实验 vs 实际 results）、匹配率（plan baseline 是否都用了）、假引用率（F04 拦截数/总引用）
   - 加测：SAR 六维 + 单篇成本/时长
4. **记录**：所有数据进 `05_评测与迭代/E1_严谨性/`

### 为什么这么做
- **每日 3 次提交配额 = 免费 A/B 实验窗口**。SAR 是唯一裁判，它的 6 维分 + 建议就是迭代信号——不利用等于浪费
- **E1 是"确定性收入"**：只要 rail 做了、实验跑了，数据一定有（不像 E2 依赖环境稳定性）。这是论文实验章节最稳的证据
- **SAR 区分度弱（0.25 vs 人类 1.52）→ 六维必须均衡**，靠 E1 找短板、阶段 4 补

### 意义
- 论文 **Experiments 3.1** 的数据（捏造率对比表：rail 组近 0 vs 对照组 X%）
- 验证 rail 的投资回报（分数提升 / 违规率下降可量化）
- 找到分数瓶颈，指导阶段 4/5 的优先级

### 验收
- [ ] 提交记录 ≥3 轮
- [ ] E1 对照组 5 篇 + 实验组 5 篇数据齐
- [ ] 捏造率/支撑率对比结论明确

## 阶段 4：写作质量达标

### 目标
- F01（写作质量 Rail）+ F07（图表生成）上线
- 论文硬指标全过：词数≥4000、图≥4、表≥6、含复杂度分析、结构完整

### 类比
产品功能没问题了，本阶段把**外观和包装**做好——审稿人（和 SAR）都看脸的。

### 具体怎么做
1. **`tools/paper_metrics.py`**：LaTeX 解析（去命令统计词数、`\includegraphics` 数图、`\begin{table}` 数表、关键词检复杂度、章节标题检结构）
2. **F01 Rail**（priority 35）：
   - `before_model_call`：注入写作硬指标规则段（操作手册压着）
   - `after_model_call`：跑 paper_metrics → 未达标项注入"缺口清单"引导补齐
3. **F07 图表生成**：
   - `tools/figure_generator.py`（matplotlib）+ `tools/table_generator.py`（LaTeX）
   - 数据从 results.json 出（F03 联动，图有出处）
   - 统一风格配置（`config/figure_style.yaml`，ICLR 模板规范）
4. **论文 v4 达标** → SAR → 对比

### 为什么这么做
- **SAR 高分画像实证**：词数 4023 vs 2461（差 1.2 分）、图 4.8 vs 0.8、含复杂度分析 77%
- **写作清晰度 10% + 图表密度是强分数信号**，F01 是"下限保障"——写作差，实验做得再好 SAR 也看不到
- **图表有数据出处 = 顺带过 F03**，一箭双雕

### 意义
- SAR 下限拉高（六维均衡的前提）
- 决赛人类评委也看论文观感，图表规范是印象分
- 论文里"系统自动产出 N 张图 M 张表"本身就是系统能力的展示

### 验收
- [ ] paper_metrics 全部指标通过（抽查与人工核对一致）
- [ ] 论文 v4 图表 ≥4 图 + ≥6 表且数据可追溯
- [ ] 含复杂度分析章节

## 阶段 5：自演进实验 + PR ★关键赌点

### 目标
- E2 自演进闭环跑通（至少 1 轮：SAR 反馈 → Auto Harness 改 rail → 热加载 → 再生成 → 对比）
- 向 openJiuwen 提真实 PR（框架贡献交付物）
- 决策：论文主叙事 T03（自演进）还是 T04（严谨性）

### 类比
机器不仅会干活、有质检员，本阶段给它装**教练**：让它自己看比赛录像（SAR 反馈）、自己改进训练计划（rail）、再上场验证。

### 具体怎么做
1. **配置 Auto Harness**：`~/.jiuwenswarm/auto-harness/config.yaml`（git.user_name/email + `GITCODE_ACCESS_TOKEN` 环境变量）
2. **小 query 试跑**（先跑通流程，别一上来就大实验）：
   `/auto-harness run --pipeline optimize_expert_harness "评估科研严谨性扩展包的缺口"`
   → 观察 assess→design→implement→verify→activate 各阶段
3. **E2 实验**（3 轮，每轮记录 `05_评测与迭代/自演进实验/`）：
   - Round 0：当前 rail 配置 → 2 篇论文 → SAR
   - Round 1：喂 SAR 反馈给 Auto Harness → 它设计/实现新 rail → 热加载 → 2 篇论文 → SAR → 对比
   - Round 2：同法再进化一轮
   - 每轮记录：进化 query / 进化产物（ExtensionDesign）/ rail diff / SAR 变化 / 成本
4. **Meta pipeline 提 PR**：让 Auto Harness 把改进提 PR 给 openJiuwen（或人工整理 rail 代码提交）
5. **决策**：E2 数据可用 → T03 主叙事；跑不通（2 周内无可用数据）→ T04 主叙事，自演进写 Future Work

### 为什么这么做
- **创新性 25% 是最高权重维度**，Agent 自演进是官方建议主题 + 前沿问题（FARS 也未解决）
- **Auto Harness 是 JiuwenSwarm 自带底座**——白送的进化引擎，接入成本远低于从零实现
- **SAR 反馈天然当进化压力测试**（fitness function）：每轮分数变化就是"进化是否有效"的证据
- **PR = 比赛硬性交付物"框架贡献说明" + 论文"自演进"证据**，一石二鸟

### 意义
- 论文最大叙事（系统自我改进的闭环 + 数据）
- 合规交付物（PR 链接）
- 风险对冲：F02/03/04 数据（T04）随时可顶，赌注输了不伤主线

### 验收
- [ ] Auto Harness 配置就绪 + 小 query 跑通
- [ ] E2 ≥1 轮完整数据（或 2 周内失败 → 记录兜底决策）
- [ ] 真实 PR 链接

## 阶段 6：论文冻结

### 目标
- 按 T03/T04 决策写定稿论文
- 复现包完成（他人可按技术包复现）

### 具体怎么做
1. 定稿结构：Abstract（叙事）/ Intro（FARS 痛点 → 我们的方案）/ Method（rail 架构）/ Experiments（E1–E4）/ Related Work（FARS + 评测论文）/ Conclusion
2. 图表、对照表、数据全部来自 `05_评测与迭代/` 记录（F03 自举校验）
3. 复现包：`REPRODUCE.md` 逐步复现（环境→配置→运行→复现论文），**在新环境自测一遍**
4. 论文过 F01/F03/F04 全校验
5. 最终版 SAR 提交

### 为什么这么做
- 论文是 40 分（SAR×4）的载体，**叙事决定创新性/重要性维度**
- 复现审核是决赛门票（TOP5 必须过），技术包质量是生命线

### 验收
- [ ] 论文冻结版（不再改内容）
- [ ] 复现自测通过
- [ ] 最终 SAR ≥ 5.5（目标）
