# 进阶版完善建议分析

> 分析对象：`进阶版完善建议_2026-08-18.md`  
> 核验范围：当前工作区的技术实现、Prototype 文档、论文与评测记录。  
> 目的：说明每项建议为何能改善项目质量、SAR 评审说服力或最终交付可信度，而非重复列出待办事项。

---

## 一、总体判断：项目的瓶颈已从“有没有能力”转为“能不能证明能力”

进阶版已经不是概念方案。工作区现有 `research-pipeline`、F02/F03/F04 三条 Rail、Rail 单测、v1–v6 论文、SAR 迭代记录和 Prototype 技术包；根目录 README 也记录了 16/16 单测通过与最高 SAR 5.8。

因此，完善建议的主张是合理的：下一阶段的收益不主要来自继续增加模块，而来自把现有能力变成一条可复跑、可审计、可追溯的证据链。

这一转变会同时改善四件事：

1. **方法可信度**：评审能确认 Rail 不是论文中的描述，而是实际执行过的约束。
2. **实验可信度**：论文中的数字、结论和对比臂可回溯至原始数据与固定协议。
3. **工程可信度**：他人可在干净环境安装并运行最小样例，不必依赖作者电脑或服务器。
4. **提交风险**：版本、密钥、路径和源码贡献的歧义会在打包前被消除。

## 二、现有事实与建议之间的对应关系

| 已有事实 | 仍存在的缺口 | 建议为何有效 |
|---|---|---|
| F02 在 `before_tool_call` 中设置 `_skip_tool`，会阻止不合规 `plan.json` 写入 | 最终交付中尚未形成可一键演示的完整安装、加载和拦截证明 | 一键复现与端到端测试把“代码存在”转成“行为可验证” |
| F03/F04 会在论文写入或任务结束时发现无来源数字、未命中引用 | 两者主要注入修正提示，未必阻止不合格 PDF 导出 | 发布前 Gate 将“建议模型修正”升级为“未通过不得发布”的可审计约束 |
| `paper.tex`、`plan.json`、`results.json` 已构成设计上的数据链 | 核心数据多位于运行时工作区，技术包缺少固定归档与哈希 | 数据入包、哈希和表格映射让评审可独立复算结论 |

## 三、P0 建议为何应优先完成

### 1. 一键复现：把说明书变成验收程序

`Prototype/code/main.py` 当前的 `--check` 只验证 `jiuwenswarm` 与 `openjiuwen` 能否导入；`--stage experiment` 在没有配置脚本时会返回成功码。这样的入口对作者自用足够，但不足以证明“第三方已成功装载 Skill、Rail 并得到审计结果”。

建议增加 `bootstrap.py`、`make reproduce` 或等价脚本，效果不是“为了自动化而自动化”，而是将交付条件明确为可机器判定的合同：依赖可安装、扩展已注册、F02/F03/F04 已加载、示例输入可运行、故意构造的错误能被检测。

这会直接改善工程评分与答辩说服力。评审面对的不是一串手工步骤，而是一条可重复执行的证据；失败时也能从非零退出码迅速定位缺包、缺配置或扩展未生效的问题。

### 2. 固化框架版本与 PR 证据：防止“论文声明”和“安装结果”脱节

当前模块调用说明称项目修改了 JiuwenSwarm 两个文件，并让扩展 Rail 进入正式装配链；但普通依赖安装可能只取得发布版 `jiuwenswarm`。如果 PR 尚未合并，复现者便可能拿到没有该改动的框架，造成“文档正确、运行结果不一致”。

`VERSION_MANIFEST.md`、可应用 patch 或指定 fork/commit 的作用，是将“改过哪些代码”变成一个精确、不可歧义的版本事实。它还能在答辩时回答三个高频问题：基于哪个上游版本？具体改了什么？别人怎样得到同一份代码？

这项工作不要求扩大框架修改范围；相反，它通过冻结范围来降低贡献真实性和兼容性风险。

### 3. 数据、论文与审计日志同包：让结论可被复算

F03 的设计目标是论文数值应能在 `results.json` 找到来源，F02 还要求计划中完成的实验具有相应结果。但若 `plan.json`、逐实验 `results.json` 和 Rail 决策日志不在最终包内，评审只能相信作者的叙述，无法独立检查。

将原始数据、拒绝日志、引用核验清单与 `audit_report.json` 固化到 `Prototype/data/`，再为关键文件提供 SHA-256 哈希，会产生一条完整的证据路径：

`论文表格/结论 → 结果文件 → 实验计划 → Rail 判定记录 → 文件哈希`。

这能降低“结果捏造”“选择性报告”“数据替换”三类质疑，并使 CFR/NFR/UCR、成本统计和消融表可以被复算。注意：数据中必须标明真实模型运行、本地重建和人工标注三种来源，避免把不同性质的材料混为实验结果。

### 4. 脱敏和模板化配置：减少提交事故，不是附属工作

工作区包含 `_ssh/`、`.zcode/` 等本地资源目录，且部分文档仍含服务器路径。即使代码本身正确，私钥、令牌、绝对路径或个人日志进入 ZIP 都会造成安全、隐私和复现问题。

以 `config.example.yaml` 及 `${MODEL_API_KEY}` 变量占位替代真实配置，可让评审清楚填写哪些参数，同时避免泄露。统一 Python 版本范围也很重要：技术 README 写的是 `>=3.11,<3.14`，运行说明若仍写 `>=3.10`，用户可能在不兼容环境中失败并误判项目不可用。

## 四、P1 建议为何会提升技术可信性

### 1. F03/F04 的发布前 Gate 是必要补强

三条 Rail 的强度并不相同：

- F02 是 **hard block**：不合规计划会被跳过工具调用；
- F03/F04 是 **detect-and-repair**：发现问题后将修正信息注入提示词，依赖后续模型行为。

这种区别并非缺陷，前提是论文如实描述。但若宣称三条 Rail 都能“强制防止”问题，就会与实际实现不符。发布前 Gate 的价值在于提供第二道、确定性的验收：论文仍有无来源数字、缺失已完成实验结果或未核验引用时，导出过程失败并留下原因。

这能让 F03/F04 保持创作过程中的柔性修复能力，同时在最终输出阶段获得确定性，形成“生成时提示修复 + 发布时强制验收”的分层机制。

### 2. F03 需要从数值集合匹配走向语义溯源

当前 F03 会将论文中的数值按两位小数与结果值集合匹配。它可快速发现明显编造的数字，是合理的第一层检查；但同一个数值可能代表不同指标、不同实验臂或不同表格位置，因此仅匹配数值可能误放行。

增加指标名、实验 ID、位置和来源字段后，Rail 的判断从“这个数字是否出现过”提升为“这句话的这个指标是否由该实验支持”。这会显著提高论文方法部分的严谨性，也让审计报告能被人类读懂。

### 3. F04 在线核验与忠实度审计解决不同问题

本地引用池命中只能说明 cite key 有对应条目；OpenAlex/arXiv 在线核验可进一步说明文献实体存在；而 claim-to-citation support 审计回答的是最严格的问题：文献是否真的支持相邻的研究主张。

三者应分层报告，不能互相替代。引用 manifest 记录查询来源、时间、标识符与结果，保证离线可复查；抽样忠实度审计则通过样本量、一致率和不确定项回应“引用存在但不支持论断”的风险。这样会改善 Related Work 的可信度，并回应 SAR 对循环性和 faithfulness 的潜在质疑。

### 4. 将 Rail API 验证纳入 CI，防止“测试绿但集成失效”

Rails 依赖 `openjiuwen` 生命周期钩子和内部模块。单元测试可以验证规则函数，却未必证明其在实际 `chat(code)` 流程中已被装配、触发并留下可见结果。固定版本矩阵、运行 `pytest -q custom_rails/tests` 并保存干净环境日志，配合 F02/F03/F04 的三条端到端测试，能够覆盖这条断层。

其关键贡献不是追求更多测试数量，而是证明每条核心主张都有对应运行证据：F02 真拦截工具、F03 真阻止无来源结果发布、F04 真阻止未核验引用发布。

## 五、v7 实验建议为何有机会突破当前上限

v6 已证明系统具有一定效果，但“full-rail 是否比强提示或单门控更有效”仍需更严格的因果设计。若只比较 full-rail 与 no-rail，分数变化可能来自提示词、任务难度、模型波动或任一单 Rail，无法证明组合机制的独特价值。

建议的组合消融把 no-rail、prompt-only、单 Rail、部分组合和 full-rail 放在相同 seed 与任务下比较，能够估计每个组件的边际贡献和组合效应。跨模型分报告则避免把某个模型偶然适配的收益误写成普适结论。T4 执行声称压力任务用于制造真实违规空间，使 UCR 不再长期处于接近零的地板区。

预注册并不会让实验更复杂；它只是先冻结样本量、指标、排除规则与停止条件，防止得到结果后再调整规则。配合独立审计或不同模型的盲审，可把“指标与 Rail 同构”的循环性质疑从隐藏风险改为透明局限，并给出缓解证据。

## 六、需要同步修正的文档一致性问题

本次核验发现，部分说明文档仍停留在早期规划状态，会稀释进阶版的完成度：

1. `03_技术实现/README.md` 的“计划中的组件”仍将 F02/F03/F04 写为待落地，而其 Rail 文件已存在。
2. 同一 README 声称源码副本含 `.git` 历史，但完善建议的静态检查认为当前副本无可用 `.git` 元数据；应以实际状态复核后只保留一个准确表述。
3. `05_评测与迭代/README.md` 仍将评测记录与 A/B 日志列为“待建”，但根目录 README 已称 v1–v6 均有记录。
4. 运行文档位置与文件名需在打包前复核，避免 README、Prototype 目录和实际文件结构不一致。

这些问题不一定代表实现缺失，但会让评审难以判断哪些功能已经完成。修正文档应与版本清单同时完成，并在冻结包后禁止各文件各自更新版本号。

## 七、优先级与收尾边界

推荐顺序仍是：

1. **P0：复现与证据封装**——入口脚本、版本冻结、数据入包、脱敏、配置模板；
2. **P1：发布 Gate 与集成验证**——明确 F02/F03/F04 强度、补齐最终验收与端到端证据；
3. **P1/P2：v7 预注册实验**——先冻结协议，再做消融、跨模型和独立审计；
4. **最终冻结**——根据结果选择 v6 或 v7，生成唯一的 `RELEASE_MANIFEST.json`，统一论文、数据、代码、SAR 与资源报告版本。

应避免在这之前扩展 F01/F05/F07 等大模块。它们可能有价值，但无法直接解决“现有三条 Rail 是否可复现、是否真正生效、是否带来独特收益”这一当前最关键的问题。新增功能会增加变量、消耗实验预算，也会让最终包更难冻结。

## 八、结论

这份完善建议的核心并不是“再做更多功能”，而是将已有的 F02/F03/F04、论文迭代和框架贡献转化为可运行、可审计、可复算、可答辩的成果。这样写能够改进项目，是因为它直接补足了科研型 Agent 项目最容易被质疑的三件事：结果是否真实、机制是否真的生效、第三方能否重现。

在当前 5.8 的基础上，优先建设证据链和严格消融，比盲目扩写论文或堆叠模块更可能提升 SAR 的方法、实验与写作说服力，也更能降低最终提交的工程与合规风险。
